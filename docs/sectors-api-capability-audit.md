Node 22.20.0 was used. The command uses native TypeScript stripping and the `react-server` condition for the `server-only` marker. The minimum endpoint for exit status is the first company-directory page: invalid/missing setup, failed directory access/validation, or output-write failure exits nonzero. Optional failures are recorded independently and do not fail the whole run. A global auth failure on the minimum endpoint, network/timeout failure or exhausted 429 stops further requests to conserve quota; skipped probes stay `UNVERIFIED`. An endpoint-specific 403/404 does not stop other probes. Exit 0 does **not** assert every capability works.

### TradingView and existing analysis

`tradingview-test` contains package manifests and dependencies only: its declared `index.js` does not exist, and its test script is a placeholder. There is **no runnable persistent worker** there. The root app uses `@mathieuc/tradingview` 3.5.2 through server-only client/session/transport modules. It starts on-demand sessions via Next routes; SSE ends after 55 seconds. `npm run dev` or `npm run start` runs the app, not a separate collector. These facts supersede any assumption that a working persistent worker already exists.

Existing phase/intelligence/inventory modules were not rebuilt in Phase 1. A persistent Node collector, shared normalized backend and PostgreSQL ingestion remain an architectural gap for Phase 2; do not deploy a long-running collector in a browser or Vercel serverless route. Lightweight Charts supports the current custom regions; this audit does not establish a TradingView official Charting Library license or redistribution entitlement.

`src/data/demo.ts` contains twelve explicitly fictional ticker scenarios and fixed scenario dates; unit tests use them. `demo-repository.ts` is dynamically imported only after the server checks `FLOWPHASE_MODE=demo`. Provider failures do not trigger a demo fallback. Existing hard-coded broker classifications/analysis thresholds are research assumptions, not verified identities or calibrated probabilities. New samples are documentation/test artifacts only and are not imported by production code.

## Freshness, limits and interpretation

The daily, broker and foreign observations end at **18 September**, the Friday preceding the audit. Diagnostic windows end at yesterday in Jakarta and exclude today's in-progress session. This does not measure provider publication lag or establish real-time entitlement. Ownership's latest **31 August** period is older by design; its release date is missing, so historical backtests must not assume period-end availability.

`diagnostic.json` records field-level non-null counts, timestamps by field, annual years, observed date range, latency and attempt metadata. Request `start`/`end` are excluded from freshness. Corporate-action event dates are recorded separately and not reported as freshness. The report mixes data periods: use `overview.latest_close_date` for price and the ownership field's own date, never one maximum timestamp for every section.

No quota/RPS headers or exact subscription limits were observed. Retry is limited to temporary 429/5xx, with exponential backoff/jitter, maximum two retries in the shared client and one in the diagnostic. Numeric/HTTP-date Retry-After is respected; a delay over ten seconds ends retries. Timeout, network, invalid JSON and non-429 4xx do not retry. Provider response bodies and exception causes are discarded from errors. Exact origin/v2 allowlisting and redirects disabled prevent credential forwarding.

Samples retain at most two records per nested array, omit credentials/account identifiers and unnecessary personal text, and label their purpose. No storage prohibition was found in the reviewed API pages; account-specific storage/redistribution terms were not available in this audit, and the public homepage fetch returned 429. These small local schema fixtures are **not a statement of publication rights**. Do not use them as a cached production feed or infer a bulk redistribution license.

## Remora feasibility and Phase 2 recommendation

| Decision                 | Evidence-based scope                                                                                                                                                                                                                                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| MVP-A — price/volume     | Feasible for a pilot: directory access, BBCA taxonomy and actual historical OHLCV work. Full-universe completeness, null OHLC prevalence and longer history must pass incremental coverage checks before claiming all-IDX coverage. Existing production charts remain TradingView; Sectors OHLCV is audit-only. |
| MVP-B — broker inventory | Feasible for a limited pilot: historical daily buy/sell lots and IDR values verified. With unknown starting holdings, label results cumulative net lots/estimated inventory. The 19 sessions sampled are not enough for the existing 20-prior-session baseline for every date/broker.                           |
| MVP-C — microstructure   | Not supported by established evidence. Hide same-second bursts, split execution, bid replenishment, cancellations and spoof/reload modules. Daily frequency does not replace tick/order-event data.                                                                                                             |
| MVP-D — ownership        | Monthly holder count and local/foreign category changes are feasible. Gate free-float, IPO allocation and scrip/scripless balance analytics until their own data is verified.                                                                                                                                   |

Day 1–2 price/volume thesis, low-volume correction and volume anomalies can be researched. Day 3 broker concentration and net inventory estimates have usable source fields. Day 4–5 crossing **candidates** can compare gross/net broker activity; daily aggregates cannot prove matched crossing, related owners or manipulation. Monthly category and holder trends can add context. No source provides the order events required for displayed-versus-executed liquidity claims.

Phase 2 should first implement incremental, resumable, quota-aware normalized ingestion with per-dataset source/ingestion/publication timestamps and quality flags, then a persistent Node TradingView collector and PostgreSQL storage. Start with a few symbols; verify full directory pagination and long-history coverage before broadening. Only then extend the price-volume evidence engine, broker pilot and monthly ownership context. Preserve SOURCE/DERIVED/ENGINEERING/CONFIGURABLE distinctions, configurable thresholds, explicit missing-data confidence penalties and transition states. Phase scores are research candidates requiring backtesting; broker codes never establish beneficial ownership. No Phase 2 database, worker, classifier or dashboard was added here.
